# M1：不変原本ファイル保存層（開発中）

## 目的

`backend/src/storage/original-file-store.ts`は、SQLiteを使うServiceを作る前に、ファイルシステムの保存・整合性検証・再起動後の判定を独立して検証するためのコンポーネントです。**現時点ではMVPの完成でも、本番保存サービスの完成でもありません。**

- 外部ユーザー向けのAPIには接続していません。
- 実際の会話・文書や認証情報を扱いません。
- 外部サービスやOllama、FTS5へ原本を転送しません。
- テストは合成テキストとOSの一時フォルダのみを使用します。

## 現時点でできること

| 操作 | 内容 |
| --- | --- |
| `stage` | 明示された絶対保存ルートに、ジャーナルを先に作成し、UUID別のステージングへ新規ファイルを保存してfsyncする |
| `promote` | ジャーナルと原本のSHA-256・バイト長を検証し、正式保存先に新規リンクを作成する（既存ファイルは上書き禁止）。検証後に一時的な別名のみ削除する |
| `inspect` | `STAGED`・`FILE_READY`・`RECOVERY_REQUIRED`を判定する |
| `listJournalIds` | 復旧対象になり得るジャーナルのIDを列挙する |
| `verifyFinal` | 正式原本の存在と内容のハッシュ・サイズを確認する |

内部の保存先構成（アプリが別途用意した専用ルートの下）：

```text
<保存ルート>/
├─ runtime/
│  ├─ journal/<UUID>.json          # 本文なしのSHA-256・サイズ・参照情報
│  └─ staging/<UUID>.part          # 未完了の場合のみ残る一時ファイル
└─ originals/YYYY/MM/<UUID>       # 原本。上書き禁止
```

ジャーナルを先に書き込むため、停止途中でステージングが完成していなければ、後から調査できます。既存の正式原本を誤って上書きしないよう、同一ボリュームで新規ファイル名を作るハードリンクを使用します。保存ルートと生成先のディレクトリについて、シンボリックリンクやジャンクションの利用を拒否する検査も設けています。

## 限界・安全上の残課題

1. **SQLiteとの二段階確定が未実装です。** `records`・`original_versions`・`storage_operations`の状態遷移は、次のService実装で扱います。`FILE_READY`はファイル配置の完了であり、DB確定や機密検査完了ではありません。
2. Windows/NTFSのハードリンク、ジャンクション、ACL、ディレクトリエントリの永続化・電源断後の回復は実機確認が必要です。ファイルの`fsync`だけで電源断耐性を完全保証しません。
3. 本番向けの保存ルート設定、排他処理、ディスク空き容量、同時実行、バックアップ、ジャーナルとDBの再照合は未実装です。競合・リンク作成失敗の際はエラーとジャーナルを残し、自動削除や上書きはしません。
4. `inspect`は復旧が必要な状態を発見するだけで、自動修復しません。シンボリックリンク検査だけでは、ローカルの悪意あるプロセスによる同時すり替えを完全に防げません。保存ルートの適切なNTFS ACLが必要です。
5. M1の暫定入力上限は5MiBです。より大きい原本・音声はM2以降でストリーミング設計と合わせて検討します。
6. GitHubリポジトリ配下を保存ルートにしないでください。実データと秘密情報をGitHubへコミットしないでください。
